Resposta às duas dúvidas
1. Como ver o que dois dispositivos publicaram simultaneamente?
É possível, mas para isso o sistema não pode simplesmente aceitar a última publicação.

No modelo atual, se dois dispositivos publicarem juntos, um dos snapshots pode sobrescrever o outro. Com o modelo novo, cada publicação vira uma generation imutável e o Firestore mantém um único ponteiro para a generation oficialmente aceita.

Exemplo:


G0 = estado comum antes das publicações

Dispositivo A publica:
G1A = G0 + item “Arroz”

Dispositivo B publica:
G1B = G0 + item “Leite”
O resultado seria:


Generation atual: G1A
Publicação concorrente preservada: G1B
Base comum: G0
O aplicativo Android mostraria uma tela como:

Publicações simultâneas detectadas
Publicação de Iasmim — Android 1
Adicionou: Arroz, 1 pacote
Alterou: 0 itens
Removeu: 0 itens
Publicada às 10:42
Publicação de Igor — Android 2
Adicionou: Leite, 1 litro
Alterou: 0 itens
Removeu: 0 itens
Publicada às 10:42
Resultado possível
Os itens não entram em conflito porque são diferentes. O app pode combinar as duas publicações automaticamente e criar uma nova generation consolidada.

Nesse exemplo, o resultado seria:


G2 = G0 + Arroz + Leite
E a tela poderia informar:

2 alterações simultâneas combinadas sem conflito.

Quem resolve cada conflito?
Minha recomendação é:

Alterações em itens diferentes
são combinadas automaticamente;
todos podem visualizar o resultado;
o owner ainda pode remover um item adicionado por outra pessoa;
a removal deixa de ser uma “decisão de conflito”, porque não houve sobreposição.
Alterações no mesmo item
o owner escolhe o valor final;
a tela mostra as duas propostas;
a escolha registra:
autor;
dispositivo;
data;
valor escolhido;
valor descartado.
Remoção versus alteração
Se uma pessoa removeu um item e a outra alterou a quantidade, isso também será um conflito explícito para o owner.

Isso atende à sua decisão:

todos podem editar a lista oficial;
o owner pode revisar os itens dos outros;
o owner pode remover itens dos outros;
somente decisões realmente ambíguas exigem uma escolha do owner.

Publicação
O Android monta um snapshot local.
Divide cada área em chunks.
Grava os chunks como candidate imutável.
Solicita a publicação à Function.
A Function compara a generation base com a generation atual.
Se ainda forem iguais, a Function publica o novo manifesto.
Se outra publicação tiver happened primeiro:
a candidate concorrente é preservada;
um conflito é registrado;
o aplicativo apresenta as duas versões.
Por que a candidate rejected não pode ser apagada
Se a segunda publicação for rejeitada e seus chunks forem apagados, não existe como saber o que aquele dispositivo continha.

Por isso, uma candidate concorrente permanece por um período de retenção, por exemplo:

7 dias para o piloto;
depois, limpeza automática;
optionally, 30 dias em produção caso seja útil manter o histórico.
A candidate não é o estado oficial. É apenas uma versão preservada para comparação e recuperação.

Remoção protegida
A remoção de um item adicionado por outra pessoa deve ser validada no backend.

Ações:

Permissões:

Ação	Membro comum	Autor do item	Owner
Confirmar item	Não	Não	Sim

Não duplicaria o aplicativo inteiro. Eu faria um flavor Android piloto com backend Firebase separado.

A parte que responde diretamente à sua primeira dúvida é:

Cada publicação simultânea será preservada como uma generation separada, e o Android mostrará um comparador com “antes”, “publicado por este dispositivo” e “publicado pelo outro dispositivo”. Alterações diferentes serão combinadas automaticamente; alterações no mesmo item serão resolvidas explicitamente pelo owner.

Isso permite observar exatamente o conteúdo publicado por cada dispositivo, em vez de apenas receber uma mensagem genérica de conflito.
